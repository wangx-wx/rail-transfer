# 同城异站换乘接驳方案

> 归档日期：2026-10-20
> 来源：grilling session（本轮需求讨论 + 多轮接口实测）
> 状态：**方案定稿，待开工**
> 上游：`spec/产品方案.md`（D69~D76）、`spec/技术方案.md`（T57~T62）

---

## 一、问题

用户查中转时，同城异站换乘只得到一行「换乘 北京南 → 上海站，等待 90 分，同城异站」。这行字无法回答真正要紧的三个问题：

- 两个站之间**怎么走**（地铁？公交？只能打车？）
- **要多久**，够不够 90 分钟
- **多少钱**、**多远**

更糟的是，「同城异站 60 分钟下限」（D13）是一个固定常数，与实际接驳耗时无关。于是会出现「等待 65 分、接驳却要 70 分」这种肉眼看不出的硬伤；反过来，等待 120 分但接驳只要 20 分时，用户也无法判断这是富余还是浪费。

此外，12306 的「同城」口径是**地级行政区**，不是通勤意义上的城市：晋中市下辖榆次、太谷西、平遥古城、和顺县，榆次到和顺县直线一百多公里。这类站对套用「市内换乘」信息会严重误导。

## 二、方案

在自研中转与官方「查中转」的结果卡片上，对**同城异站换乘**提供「查接驳」：

- 卡片级一个按钮，点击后并行查询该行程所有同城异站换乘点的**公共交通**与**打车**方案
- 每类只给一条：公交取耗时最短，打车取唯一
- 换乘行内显示摘要，展开后看完整详情（线路名、上下车站、步行距离、里程、直线距离）
- 根据「等待 − 接驳耗时」给出接驳紧张度标记，只标记、不删除、不改排序
- 站间直线距离超过 50 km 视为「跨城接驳」，只给一行事实、不给市内交通方案
- 站点坐标缺失时不提供接驳，按钮禁用并说明原因

数据源为腾讯位置服务，经 Worker 转发，key 不出现在前端。

## 三、用户故事

1. 作为同城异站换乘的旅客，我想看到从上一程到达站到下一程出发站的接驳方案，以便判断换乘等待够不够。
2. 作为旅客，我想同时看到公共交通与打车两类方案，以便在时间和花费之间权衡。
3. 作为旅客，我想看到接驳耗时，以便算出实际可用余量。
4. 作为旅客，我想看到接驳价格，以便估算全程花费。
5. 作为旅客，我想看到接驳的路线里程与两站直线距离，以便知道这趟接驳究竟多远。
6. 作为旅客，我想看到公交方案的具体线路名与上下车站，以便真的能照着走。
7. 作为旅客，我想看到公交方案的总步行距离，以便判断拖着行李是否可行。
8. 作为旅客，我想看到公交方案的换乘次数，以便判断路线复杂度。
9. 作为旅客，我想在公交方案不含地铁时看到「无地铁」标签，以便知道有没有轨道交通可用。
10. 作为旅客，我想在公交线路可能赶不上末班、首班未发或停运时看到标记，以便决定是否改打车。
11. 作为旅客，我想在换乘行直接看到「等待 90 分 → 公交 52 分余 38 分 / 打车 28 分余 62 分」，以便一眼判断可行性。
12. 作为旅客，我不想接驳价格混进火车票的「二等座参考价」，以免误以为票价变了。
13. 作为旅客，我想在连打车都赶不上时看到「接驳时间不足」，以便直接排除该方案。
14. 作为旅客，我想在公交赶不上但打车赶得上时看到「需打车」，以便知道要多花钱。
15. 作为旅客，我想在时间余量很小但尚可赶上时看到「接驳紧张」，以便提前准备。
16. 作为旅客，我不想在同站换乘时看到接驳区，以免界面被无关信息占据。
17. 作为旅客，我不想在相距上百公里的两个站之间看到「市内地铁方案」，以免被误导。
18. 作为旅客，我想在站点位置未知时看到明确说明并看到按钮被禁用，以便知道这不是查询失败。
19. 作为旅客，我想在自研中转与官方中转两条通路里看到一致的接驳展示，以免规则不一致。
20. 作为旅客，我想只点一次就查完一张卡片上所有同城异站换乘，以免逐条点击。
21. 作为旅客，我不想同样的两个站被重复查询，以免等待时间和额度被浪费。
22. 作为旅客，我想在网络失败时能手动重试，以便临时故障后不用重新发起整个查询。
23. 作为旅客，我想在腾讯不支持该城市公交查询时看到具体原因而不是一个反复无效的「重试」按钮。
24. 作为旅客，我想在接驳服务未配置时看到明确提示，而不是空白。
25. 作为旅客，我想在换乘行看到完整的「到达站 → 下一程出发站」，而不只是到达站。
26. 作为旅客，我想在打车价来自路况估算时看到「路况估算」，来自计价规则推算时看到「估算」，以便知道可信度不同。
27. 作为旅客，我想在有过路费时看到单独一行的过路费，以免被「总价」误导。
28. 作为旅客，我想在接驳方案查不到时看到「暂未获取到接驳方案」，而不是空白或「0 分钟」。
29. 作为旅客，我想在换乘等待与接驳耗时匹配良好时不被任何标记打扰，以便专注比较方案。
30. 作为维护者，我想站坐标在构建期一次生成、运行期零网络，以便不影响线上请求量与合规边界。
31. 作为维护者，我想站坐标抓取中断后能续跑，以便不必从头再来。
32. 作为维护者，我想接驳的判定与拼装集中在纯函数里，以便不依赖网络与 DOM 就能覆盖全部边界。

## 四、实现决策

### 4.1 产品范围（D69~D76）

- **D69 覆盖通路**：自研中转与官方「查中转」两条通路都提供接驳，共用同一套判定与展示。仅覆盖**同城异站**；同站换乘不显示接驳区。**D33 失效**（原「高德 v1 不接入、使用者自备 key」），D62 中「高德接驳时间留 v2」一句随之失效。
- **D70 触发方式**：手动懒加载。每张行程卡片一个「查接驳」按钮，点击后并行查询该卡片内所有同城异站换乘点的公交与打车，按钮 loading 到全部返回。
- **D71 方案数量**：公交 1 条（多条候选中取耗时最短）+ 打车 1 条；两类始终都给，不提供备选列表。
- **D72 展示形态**：换乘行内摘要 + 原位展开详情（沿用卡片已有的折叠交互）。余量按公交、打车**各算各的**。接驳价格不计入「二等座参考价」，单独一行并标注不含接驳。
- **D73 标记**：与既有换乘标记合并为一排标签，靠文案区分。三档判定沿用既有阈值 20 分钟（不新增常量）：
  - 等待 − 打车耗时 < 0 → 「接驳时间不足」
  - 公交赶不上、打车赶得上 → 「需打车」
  - 等待 − 较快方式耗时 < 20 分 → 「接驳紧张」
  - 另有：「无地铁」「跨城接驳」「可能错过末班」「首班未发」「停运」
- **D74 降级口径**：
  - 网络失败 / 超时 → 显示失败原因 + 重试按钮
  - 腾讯业务错误（不支持该城市、无可达路线等）→ 显示原因，不提供重试
  - key 未配置 → 「接驳服务未配置」
  - 查不到方案 → 「暂未获取到接驳方案」，有坐标时附直线距离
  - 站点坐标缺失 → 按钮禁用 + 「未获取到站点位置」
  任何情况下不显示空白，也不显示「0 分钟」。
- **D75 同城口径与跨城判定**：以两站直线距离判定。> 50 km 视为跨城接驳，只给一行「跨城接驳 · 直线约 N 公里 · 不提供市内交通方案」，不给按钮。缺任一坐标时不提供接驳。**换乘时间窗判定不变**（同城异站仍按 60 分钟下限），本决策只影响接驳展示，不改变既有换乘可行性与结果数量。
- **D76 打车价格口径**：优先使用腾讯驾车结果中的打车费（UI 标「路况估算」）；该字段缺失时，按 Top 40 城市出租车计价表（起步价 / 公里价 / 夜间加价）沿里程推算区间（标「估算」）。两种来源在界面上必须可区分，不得混为一种。过路费 > 0 时单独一行。夜间加价按**出发时刻**判断（22:00~06:00）。

### 4.2 数据源与代理（T57~T58）

- **T57 数据源**：腾讯位置服务 WebService。公交用公交路线规划，打车用驾车路线规划。三个必须遵守的上游约束：
  - 坐标顺序是 **`lat,lng`（纬度在前）**，与高德相反
  - 公交价格字段单位在「无火车时为分、含火车时为元」之间摇摆，必须显式传参统一为分，前端统一按分换算
  - 公交响应**没有**步行距离汇总与换乘次数字段：步行距离需累加各步行段，换乘次数需数乘线段
- **T58 Worker 端点**：新增两个语义化端点，分别对应公交与驾车，不合并——一侧失败不应拖垮另一侧。沿用既有的薄管道、口令与错误分类约定：
  - **不启用** Worker 缓存（接驳结果由前端内存缓存，与 D72/Q17 一致）
  - 上游 key 由 Worker secret 注入，前端不可见；异常信息必须脱敏，不得回传含 key 的 URL
  - 重试由前端触发，Worker 不自动重试
  - 腾讯返回 HTTP 200 + 业务状态码，需按业务码分类：配额与瞬时错误可重试，业务性无结果不可重试

### 4.3 站点坐标产物（T59）

- **T59**：接驳需要**站点级**坐标，而现有产物只有城市级（同城只取第一个站、主动丢弃了城内差异），不能复用。故新增站点坐标产物：
  - **主数据源**：12306 小程序车站地址接口，按电报码精确查（实测 24 站样本命中 91.7%，主要城市与地级市 100%）。**2026-10-20 全量实测结果：3404 站命中 2879（84.6%）**，缺 525 站；续跑只补到 3 个（补入段命中率 ≈0%），确认是接口本身没有这些站的坐标，而非抓取失败
  - **范围**：全量 3404 站。单站城市永远不会触发同城异站换乘，但省下的量不足 3%，不值得为此增加判断分支
  - **节奏**：3 并发、每路 1.0 秒间隔；某一路连续 3 次非 200 则把该路间隔拉到 2 秒；连续 5 次非 200 全部停止并保存进度；支持断点续跑，重跑只补缺失项
  - **缺失兜底**：腾讯地理编码，仅当地址解析的可靠性指标达到「较准」且精度级别达到「可用」阈值时采用
  - **仍缺失**：不写坐标，运行时按缺坐标处理（禁用接驳）
  - **明确排除的方案**：① 按车次运行信息批量取坐标——实测覆盖率更差（部分车次经停站缺坐标，恰是县级与新站），且要先按站查大屏车次，总成本更高；② 腾讯按城市枚举火车站——实测补不到目标站，且 POI 站名带「火车站」「车站」后缀，与 12306 站名不一致，靠名字匹配不可靠
  - **产物加载**：单独文件、动态 import，进入中转结果时才加载，不增加主包体积
  - **读取封装**：组件不直接 import 产物，统一经坐标查询模块，以便「缺坐标」分支可被单测覆盖

### 4.4 前端编排与数据模型（T60~T62）

- **T60 编排与缓存**：接驳查询的编排是纯函数模块，取数通过注入的接口，便于零网络单测（沿用买短乘长已有的注入式写法）。结果缓存在**前端内存**，键为「出发站码 → 到达站码」：
  - 同一查询内相同站对只请求一次
  - 跨查询复用（接驳与乘车日期无关）
  - 仅在页面刷新时清空
- **T61 数据模型与组件**：换乘点模型目前只保存**到达站**，同城异站需要并列展示「到达站 → 下一程出发站」，故新增下一程出发站字段——只加字段，不改换乘可行性判定逻辑。接驳展示抽为一个共用组件，由自研列表与官方中转列表同时使用。
- **T62 官方通路的站名反查**：官方中转的行程字段只有站名、没有站码，需复用既有的「站名 → 站码」反查。反查失败时禁用按钮并以提示说明「未识别换乘站」，不做城市级近似（会差几十公里）。

## 五、测试决策

**好的测试**：只断言外部可见行为——给定输入（站对、坐标、上游响应）得到什么展示模型；不针对内部调用顺序、私有函数或 DOM 结构细节。时间、随机、网络一律注入。

| 接缝 | 测什么 | 既有先例 |
|---|---|---|
| 纯函数编排层（主接缝，覆盖绝大多数用例） | 直线距离计算；50 km 跨城判定；缺坐标降级；三档标记；公交取耗时最短；步行距离累加；换乘次数统计；价格单位换算；计价表区间估算；错误分类（可重试 / 不可重试） | 买短乘长的注入式编排测试 |
| Worker 路由面 | 两个新端点的参数校验；key 未配置；上游业务码分类；错误脱敏；无缓存写入 | Worker 入口测试（真实 workerd + 注入 fetch） |
| 坐标读取封装 | 产物结构 → 查询结果；缺失站返回空；阈值判定 | 城市解析模块测试 |
| 共用接驳组件 | 摘要文案；展开详情；按钮禁用与提示；加载态；仅网络错误出现重试 | 自研列表的组件测试 |

**不单测**：坐标产物生成脚本（与既有的可达图、城市坐标生成器一致，靠产物结构测试兜底）；腾讯上游的真实响应（用固化样本）。

## 六、不在范围内

- 地图展示、导航外链
- 跨城（> 50 km）站对的接驳方案
- 接驳价格计入火车票总价
- 接驳备选方案列表（只给一条）
- 站名反查命中率的优化
- 用 12306 官方的同城换乘预留时间校准既有 60 分钟常数
- 多数据源切换（不引入第二家地图服务）
- 接驳结果持久化（localStorage / Worker 缓存 / 跨设备）
- 修改换乘时间窗常数或换乘可行性判定

## 七、补充说明

**已实测确认（2026-10-20）**

- 站坐标全量抓取：3404 站 → 2879 站有坐标（84.6%），耗时约 40 分钟（3 并发 × 1.0s）；缺失站点经续跑确认不可补。产物为独立 chunk（gzip 35 kB），未进主包，T59 的「动态 import」成立。
- 腾讯公交响应样本（北京南 → 北京西）：地铁方案 8056 米 / 30 分 / 票价 400 分，三段步行 49+257+74 = 380 米，两段乘车；驾车 11057 米 / 16 分 / 过路费 0。**该样本里 `taxi_fare` 未出现**，故计价表兜底是主路径而非兜底路径——这一点在真实使用中需继续观察。

**待实测确认（不阻塞设计，不成立时走已定降级路径）**

1. 腾讯驾车结果的打车费字段是否稳定返回。若普遍缺失，Top 40 计价表即为主路径。
2. 官方中转结果「站名 → 站码」的实际命中率。只影响有多少场景被禁用。
3. 公交接口返回的候选方案是否严格按耗时升序（官方只承诺默认策略为「时间短」，未承诺数组排序）。实现时自行比较取最小。

**已知维护成本**：出租车计价表需人工维护，会随城市调价而过时。这是选择「给价」而非「不给价」的代价，需在文档中保留更新入口。**当前实现只收录了北京一城**（`web/lib/taxiTariff.ts`），其余城市在 `taxi_fare` 缺失时不显示价格——扩充时逐条补，不按「大致同类城市」外推。

**合规边界**：站点坐标抓取属于构建期一次性产物生成，与既有的可达图、城市坐标生成器同类，不属于运行期抓取。运行期接驳查询为人工触发、按站对缓存、单次最多两类请求，符合项目「个人低频」的定位。

**同名概念区分**：本功能中的「同城」沿用既有站表口径（地级行政区），**不修改**该口径；跨城阈值只作用于接驳展示，用于避免把百公里级站对渲染成市内换乘。
