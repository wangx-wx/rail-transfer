## 一、技术定位

**目标**：把产品方案（D1~D38）落成一个可运行的工程——GitHub Pages 前端 + Cloudflare Workers 代理。

**三条硬约束**（全部来自实测，见产品方案 4.1 / 5.10）：

| 约束 | 数值 | 来源 |
|---|---|---|
| 子请求 / invocation | **50**（**与 Cache API 调用共享**） | Workers Free 官方文档 |
| 同时出站连接 | 6 | 同上 |
| CPU 时间 / invocation | **10 ms**（**网络等待不计入**） | 同上 |

**CPU 不是瓶颈**（T1 的薄管道原则使 Worker 几乎不解析业务 JSON），**子请求配额才是**——分段流式（D37）即为解决它而生。

## 二、总体架构

```
浏览器（GitHub Pages 静态页）
    │  /api/*（相对路径，本地走 Vite proxy）
    ▼
Cloudflare Worker（代理层：转发 + cookie + CORS + 口令 + 缓存）
    │  fetch
    ▼
12306 内部接口（kyfw.12306.cn）
```

**薄管道原则**：Worker 把 12306 的**原始 JSON** 回给前端；**解析 / 合并 / 筛选 / 排序 / 渲染全在前端**。理由（T1）：

1. **CPU 10ms 撑不住厚 Worker**——lcquery 单枢纽响应约 30KB，15 枢纽 ≈ 450KB，`JSON.parse` 计入 CPU，很可能撞限；浏览器无此约束。
2. **分段流式（D37）本就是前端编排**——状态天然在前端。
3. **越薄越安全**——5.10 实测 Workers 复用 isolate 导致模块级状态泄漏；薄管道无状态，绕开此坑。

### 3.3 运行时

| ID | 决策 | 状态 |
|---|---|---|
| T8 | 余票接口的 cookie：**每次 invocation 现取现用**（先 `leftTicket/init`），用完即弃，不缓存 | 有效 |

## 五、接口契约

四个语义化端点（T2），全部 1:1 映射上游接口。**返回上游原始 JSON**（T1）。

| 端点 | 上游接口 | 关键参数 | cookie |
|---|---|---|---|
| `GET /api/left-ticket` | `/otn/leftTicket/queryG` | `from` `to` `date` | 需要（T8） |
| `GET /api/transfer` | `/lcquery/queryG` | `from` `to` `date` `hubs`(逗号分隔) | 不需要 |
| `GET /api/stopover` | `/otn/czxx/queryByTrainNo` | `train_no` `from_station_no` `to_station_no` `date` | 不需要 |
| `GET /api/price` | `/otn/leftTicket/queryTicketPrice` | `train_no` `from_station_no` `to_station_no` `seat_types` `date` | 不需要 |

**`/api/transfer` 是扇出端点**：Worker 对 `hubs` 里每个枢纽各发 1 次上游请求（段内串行，T12），返回 `[{hub, ok, data|error}, ...]` 的数组——**每项内是上游原始 JSON**，前端逐项解析。

**请求头**：`X-Access-Token: <口令>`（T15）。

**失败形态**：单枢纽真错误时该项标 `error`，不中断同段其余枢纽（T13/T14）。空 `data` 不算错误。

## 六、请求编排（分段流式，D37）

前端分多次请求，每段独立 invocation，**各有 50 子请求配额**，自然分摊。结果到达即追加显示。

| 段 | 内容 | 子请求预算 |
|---|---|---|
| A | 直达（余票）+ 官方中转基线 | `init 1 + query 1` + `cache 2` + `基线 1 + cache 2` = **7** |
| B / C / D | 每段 6 枢纽（T11） | `6 fetch + cache 2` = **8** 各 |
| E | 买短乘长（**仅直达无票时触发**，D23） | `init 1 + 3 query + cache 2` = **6** |
| | **最坏合计** | **7 + 8×3 + 6 = 37** ✓ 余 13 次 |

**缓存命中时**：整段 `cache.match` 命中 → 仅 1 子请求，预算进一步宽松。

**为何不选扇出转发（D38）**：见产品方案 4.1。

### 6.1 城市→站点表（T22）

分两半，**均可静态产出**：

| 部分 | 做法 | 依据 |
|---|---|---|
| **城市分组**（432 城市 → 各自车站） | 解析 `station_name.js` 字段 7（城市名）直接分组，**纯机械、零查询** | 已验证：长沙含 `CSQ`+`CWQ`、徐州含 `XCH`+`UUH`、十堰含 `SNN`+`OUN`，与产品方案第六节的坑吻合 |
| **哪几个是主要站** | 构建期脚本：对每个城市用若干**远距离大站**做对端采样，按到发站出现频次取 Top-N；**产物 checked in，运行时零网络** | 已验证收敛良好：上海 虹桥(148) 上海(37) 上海南(20) 松江(18) 练塘(1)；广州 广州南(162) 白云(68) 广州北(34) 广州(22) 新塘(8)。尾部断崖，Top-N 天然过滤市郊小站 |

> ⚠️ **必须记录的局限**：**主站不是城市的固有属性，而是随 OD 变化**——实测北京→上海用北京南(48)，北京→武汉用北京西(56)，北京→哈尔滨用北京朝阳(22)。静态清单**不可能对每条 OD 都精确**，它只是**枢纽枚举的候选起点**；真正的过滤交给下游换乘可行性筛选（D12/D13）。不可让静态清单承担它做不到的事。
