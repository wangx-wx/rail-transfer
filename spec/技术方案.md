## 一、技术定位

**目标**：把产品方案（D1~D38）落成一个可运行的工程——GitHub Pages 前端 + Cloudflare Workers 代理。

**三条硬约束**（全部来自实测，见产品方案 4.1 / 5.10）：

| 约束 | 数值 | 来源 |
|---|---|---|
| 子请求 / invocation | **50**（**与 Cache API 调用共享**） | Workers Free 官方文档 |
| 同时出站连接 | 6 | 同上 |
| CPU 时间 / invocation | **10 ms**（**网络等待不计入**） | 同上 |

**CPU 不是瓶颈**（T1 的薄管道原则使 Worker 几乎不解析业务 JSON），**子请求配额才是**——分段流式（D37）即为解决它而生。

## 二、总体架构

```
浏览器（GitHub Pages 静态页）
    │  /api/*（相对路径，本地走 Vite proxy）
    ▼
Cloudflare Worker（代理层：转发 + cookie + CORS + 口令 + 缓存）
    │  fetch
    ▼
12306 内部接口（kyfw.12306.cn）
```

**薄管道原则**：Worker 把 12306 的**原始 JSON** 回给前端；**解析 / 合并 / 筛选 / 排序 / 渲染全在前端**。理由（T1）：

1. **CPU 10ms 撑不住厚 Worker**——lcquery 单枢纽响应约 30KB，15 枢纽 ≈ 450KB，`JSON.parse` 计入 CPU，很可能撞限；浏览器无此约束。
2. **分段流式（D37）本就是前端编排**——状态天然在前端。
3. **越薄越安全**——5.10 实测 Workers 复用 isolate 导致模块级状态泄漏；薄管道无状态，绕开此坑。

### 5.2 initCookie 的 HTML 误判（直达查询失败的根因）

**症状**：查直达永远返回「被拦截：302 → error.html」，而查中转正常。

**根因**：`initCookie` 复用了 `classify()` 判响应，但 **`/otn/leftTicket/init` 返回的是 HTML 页面（`content-type: text/html`），不是 JSON**。`classify` 把「非 JSON」判为错误 → cookie 被丢弃 → 后续 `queryG` 无 cookie → 被 WAF 拦成 `302 → error.html`。

中转不需要 cookie，所以完全不受影响——这个「只有直达失败」的对比正是定位线索。

**修复**：`initCookie` 不再用 `classify`，只判真错误（网络失败 / 被拦 / HTTP 非 200）。

**附带澄清**：此前把该现象归因为「IP 被 12306 风控」是**误判**。补测 50 次连续带 cookie 查询**全部成功**，无速率限制。无 cookie 直查返回 `302 → error.html` 是 5.3 早已记录的正常 WAF 行为，不是封禁。

### 5.3 票价：执行票价 vs 公布票价（实现阶段实测）

12306 有两个票价接口，**对同一趟车给出不同价**：

| 车次 | 类型 | `queryTicketPrice`（按车次） | `queryAllPublicPrice`（按 OD） |
|---|---|---|---|
| Z281 普速 | 票价不浮动 | ¥177.5（硬座） | **¥177.5** ← 一致 |
| G531 高铁 | 票价浮动 | 10-07 ¥661 → 10-08 **¥626**（随日期变） | **¥795**（固定不变） |

**结论**：`queryTicketPrice` 随日期浮动 = **执行票价（实付价）**，官网展示的就是它；`queryAllPublicPrice` 固定 = **公布票价（原价）**。**故用前者**。

**席别码**：`queryTicketPrice` 返回同名键（数字码带 `A` 前缀，`9`→`A9`）：

| 界面席别 | 高铁码 | 普速码 |
|---|---|---|
| 二等座 | `O` | — |
| 一等座 | `M` | — |
| 商务座 | `9` | — |
| 硬座 | — | `1` |
| 软座 | — | `2` |
| 硬卧 | — | `3` |
| 软卧 | — | `4` |
| 高级软卧 | — | `6` |
| 无座 | `WZ` | `W`（实测高铁无座价恒等于二等座价） |

> ⚠️ **`seat_types` 参数必须传该车次自己的码串**（不是固定的 `OM9WZ`）。
> 12306 从左到右解析该串，**遇到车次不支持的码就立即截断**——传 `OM9WZ` 给普速车 K767（首个 `O` 不支持）返回空 `data`。
> 码串来源：余票响应 `result[]` 第 35 列（`COL.seatTypes`）／中转响应 `fullList[].seat_types`。
> 实测：G531=`9MOO`、K767=`1341`、G8735=`POMO`。官网自身也是这么做（`seat_types=c9[35]`）。

**码→中文名映射**：用 **12306 官方表** `seatTypeCodeForName`（取自 `queryLeftTicket_end_js.js`），固化为 `shared/constants.ts` 的 `SEAT_CODE_NAME`。原「按值取、不映射」的说法已被推翻——普速车的数字码必须映射才有可读名。

**取价规则**：只认带 `¥` 前缀的字符串值；其余（`train_no` / `OT` / 纯数字内部码）忽略。

**价格字段格式**：`{"O":"¥626.0","WZ":"¥626.0","train_no":"..."}`，另有纯数字的（如 `"2":"6260"`）是分为单位的内部码，不用。

**回归**：曾用写死的 `OM9WZ` 查价，高铁正常、普速车（K/T/Z/数字车次）全部返回空 → 前端显示「查价失败」。修复即改为回传车次自带的 `seatTypes`。

### 5.4 请求量：为何用懒加载

`queryTicketPrice` **按车次**查，一趟车 1 次请求。直达 55 趟 = 55 次，超 Workers 50 子请求上限（T1）。故：

- **直达**：每张卡片「查价」按钮，点击才查（1 次请求）
- **中转**：结果出来后自动查**最优一条**的两程（2 次请求，D21），其余手动点

## 六、请求编排（分段流式，D37；2026-10-08 按 D56 重订）

前端分多次请求，每段独立 invocation，**各有 50 子请求配额**，自然分摊。结果到达即追加显示。

| 段 | 内容 | 子请求预算 |
|---|---|---|
| A | 直达（余票） | `init 1 + query 1` + `cache 2` = **4** |
| B.. | 自研中转：按边扩展（D56/T42），每次 = 1 次 `leftTicket` | 每段受 T41 硬上限约束，单段 50 配额内 |
| E | 买短乘长（**仅直达无票时触发**，D23） | `init 1 + 3 query + cache 2` = **6** |

⚠️ **2026-10-08 变更（D56/T41）**：原「每段 6 枢纽」的分段方式随官方路线一并废弃（T11/T12 失效）。自研后请求从「枢纽级」变为「边级」：

```
一次换乘：2 × |枢纽| —— 实测 37 枢纽 → **74 次**
二次换乘：|枢纽| + |枢纽|² + |枢纽| —— 实测 37 枢纽 → **363 次**（逼近 400 硬上限）
控制：并发闸门 ≤3 + 相邻请求 ≥300ms + 单次查询硬上限 400（T41，暂定）。
     按 300ms 间隔折算，一次换乘约 22 秒、二次换乘约 110 秒——前端 UI 必须先弹请求量预估（T50）
```

⚠️ **2026-10-13 变更（T40/T49/T50/T51/T52）**：上表口径**未计入经停补查**（回头判定，实测的大头），且枢纽经几何硬砍后大幅收缩。

⚠️ **2026-10-15 变更（T54/T55/T56）——上两段均已过时**。D68 改为交互式选择后 D 只有 1~2；T55 同城归一（同城只查一次）；T56 删除经停补查。**当前实际口径**：

```
枢纽 D：用户选中 1~2 个（不再默认 12）
枚举边：一次换乘 2D / 二次换乘 D²+2D，且按**城市对**去重（T55）
        → D=2 实测仅 **6 次**（北京→上海：北京→天津、北京→济南、天津→上海、济南→上海、天津→济南、济南→天津）
经停补查：**已删除**（T56）
合计：选 1 个 ≈ 2 次 / 0.6 秒；选 2 个 ≈ 6 次 / 1.8 秒（间隔 300ms 折算）
       —— 实测（模拟上游按城市展开 + 1.5s 往返）选 2 个 **6 次 / 5.5 秒**
控制：并发闸门 ≤3 + 相邻请求 ≥300ms（数值不变）；maxEdges 按 D 自适应
```

**请求量已不再是瓶颈**（T56 后个位数），T50 的 15 秒弹窗实际成为兜底。

**缓存**：整段 `cache.match` 命中 → 仅 1 子请求，预算进一步宽松。**编排仍走分段流式**（每次前端请求 = 1 个独立 invocation，各 50 配额）。

**为何不选扇出转发（D38）**：见产品方案 4.1。

### 6.1 城市→站点表（T22）

分两半，**均纯静态、零网络**：

| 部分 | 做法 | 依据 |
|---|---|---|
| **城市分组**（432 城市 → 各自车站） | 解析 `station_name.js` 字段 7（城市名）直接分组，**纯机械、零查询** | 已验证：长沙含 `CSQ`+`CWQ`、徐州含 `XCH`+`UUH`、十堰含 `SNN`+`OUN`，与产品方案第六节的坑吻合 |
| **哪几个是主要站** | 一次性采样的**产物固化为常量**（`MAJOR_CITY_MAIN_STATIONS`），生成时零网络 | 采样按到发站出现频次取 Top-N，收敛良好（尾部断崖，天然过滤市郊小站） |

**代表站**：优先同名站（如 北京→`BJP`），否则取该城市第一个站。全部 432 城市都有代表站兜底，保证任意城市可查。

**查询职责（D18/D19/T35）**：余票与中转查询均只传代表站码，上游会覆盖同城其他车站。`stations` 清单用于排除起终点城市的换乘枢纽，不用于增加起终点站对请求；城市覆盖不增加请求预算。该接口行为已实测确认，后续无需重复质疑或验证。

> **为什么不用联网采样**：生成时需联网对 12306 发大量请求，与 D31「个人低频」定位不符，故改为纯静态。（初版生成器曾联网采样；当时观察到的查询失败后被定位为 cookie bug，非风控，见 §5.2。）

> **静态清单的用途边界**：不同线路实际使用的主站会变化——实测北京→上海用北京南(48)，北京→武汉用北京西(56)，北京→哈尔滨用北京朝阳(22)。这不影响 D19/T35：实际上下车站以接口返回为准，不能据静态清单或前端未逐站展开推断接口缺少同城覆盖。
