## 一、部署架构：纯 GitHub Pages 走不通

### 1.1 实测证据

在决定架构前，实测了 12306 接口的跨域行为（`kyfw.12306.cn`）：

| 测试项 | 命令 | 结果 |
|---|---|---|
| 带 `Origin` 的 GET | `curl -H "Origin: https://example.github.io" .../otn/leftTicket/init` | HTTP 200，**无 `Access-Control-Allow-Origin`** |
| `OPTIONS` 预检 | `curl -X OPTIONS .../lcquery/queryG` | **HTTP 302**，预检直接失败 |
| JSONP 回调 | `queryG?...&callback=cb123` | **不支持**，原样返回纯 JSON，无回调包裹 |

**结论：三条路全部堵死。浏览器中运行的 GitHub Pages 页面无法直接调用 12306 接口，必须有服务端代理层。**

### 1.2 采用架构

```
浏览器（GitHub Pages 静态页 / 本地 localhost）
        ↓  fetch
代理层（本地 Node 服务 → 未来可换 Cloudflare Workers）
        ↓  fetch
12306 内部接口（kyfw.12306.cn / mobile.12306.cn）
```

**分两阶段实施：**

| 阶段 | 形态 | 触发条件 |
|---|---|---|
| **阶段一（当前）** | 代码托管 GitHub，服务端跑 localhost | 默认。零合规风险，与设计方案第 9 节定位一致 |
| **阶段二（可选）** | 增加 Cloudflare Workers 代理 | 需要手机 / 外网访问时才启用 |

**代码结构要求**：把「取数层」（`src/source-*.mjs`）与「代理层」（`server.mjs` / `worker.mjs`）分离，使阶段一→阶段二无需改动取数逻辑。

## 二、Cloudflare Workers 免费额度（官方文档实测）

来源：[Pricing](https://developers.cloudflare.com/workers/platform/pricing/)（页面标注更新 2026-08-28）、[Limits](https://developers.cloudflare.com/workers/platform/limits/)（2026-09-05）。

| 项目 | Free 计划 | Paid（$5/月） |
|---|---|---|
| 请求数 | **100,000 / 天** | 1000 万 / 月 |
| CPU 时间 | **10 ms / 次调用** | 5 分钟 |
| 内存 | 128 MB | 128 MB |
| 子请求（subrequest） | **50 / 次请求** | 10,000 |
| **同时出站连接数** | **6 / 次请求** | 6 |
| 静态资源请求 | 免费且不限量 | — |

**官方原文**：「Cloudflare does not bill for subrequests you make from your Worker.」
→ 一次用户查询虽需发出约 31 个子请求，**但只计 1 个计费请求**。

> ⚠️ **未验证**：注册流程是否要求绑定信用卡。官方文档未提及，本次未走注册流程。**启用阶段二前需自行确认。**

### 2.1 三条会卡住设计的限制

| # | 限制 | 对本项目的影响 | 应对 |
|---|---|---|---|
| ① | **同时出站连接 6 个** | 15 个枢纽并发发出必然超限 | **必须做并发闸门，每批 ≤6**；设计方案原有的「串行 + 300~800ms 间隔」方向正确，需在代码中显式实现 |
| ② | **子请求 50 / 次** | 15 枢纽 × 2 页 = 30 尚可；若分页到 3~4 页则 15×4=60 **爆限** | **必须设分页上限** |
| ③ | **CPU 10 ms / 次**（Free 不可提高） | 网络等待不计入 CPU，但 **JSON 解析计入**。31 份 × 30KB ≈ 1MB JSON 的解析 + 合并去重 + 打分可能贴近 10ms | 撞限时把合并逻辑挪到前端，Worker 只做纯转发 |

## 三、中转算法复核（对设计方案的两处修正）

算法主选方案为**路线 B：官方 Top-N 复用 + 强制枢纽枚举**，理由见设计方案。本轮针对 `middle_station` 的展开行为做了专项复核，**发现设计方案 v3 的描述有两处不准确**。

### 3.1 修正一：展开规则不是「该城市全部车站」，而是「该城市车站组 ∩ 该 OD 可达集」

复核方法：用 `spike/station_name.js` 的城市字段（第 8 列）比对实测展开结果。

| `middle_station` | 站名 | city 字段 | 实测展开结果 |
|---|---|---|---|
| `NKH` | 南京南 | 南京 | `[南京南, 南京]` ← **非城市名同名站也展开** |
| `ENH` | 合肥南 | 合肥 | `[合肥, 合肥南]` |
| `JAK` | 大明湖 | 济南 | `[济南, 济南西]` ← **传的站自己都没进结果** |
| `XCH` | 徐州 | 徐州 | `[徐州, 徐州东]` |
| `LAJ` | 兰州西 | 兰州 | 在 `XAY→WAR` 中展开为 `[兰州, 永登北, 兰州西]`；在 `LZJ→HZH` 中仅 `[兰州西]` |
| `ASH` | 安亭北 | 上海 | ❌ `没有查询到中转方案` |
| `UQJ` | 龙泉寺 | 兰州 | ❌ 同上 |
| `TIE` | 天府机场 | 成都 | 仅过滤自身 `[天府机场]` |

**修正后的规则**：服务端取「给定码所属车站组」∩「该 OD 的预计算可达集」，并剔除出发站 / 到达站本身。

**工程含义**：
- 用 `station_name.js` 城市字段程序化生成「城市 → 代表站码」**可行**，比硬编码可靠；
- 但**代表站必须选主要客运站** —— 小站（安亭北、龙泉寺、骆驼巷）即使 city 字段正确，不在可达集内仍会静默失败；
- 设计方案已记录的坑确认成立：`CWQ` 是**长沙南**而非长沙（长沙为 `CSQ`），`UUH` 是**徐州东**（徐州为 `XCH`）。

### 3.2 修正二：目的地站需过滤，反方向站反而可用

实测 `VNP`(北京南) → `AOH`(上海虹桥)，日期 2026-10-07：

| `middle_station` | 结果 |
|---|---|
| `AOH`（目的地本身） | ❌ `没有查询到中转方案` |
| `HZH`（反方向的杭州） | ✅ 返回 10 条方案（杭州东 / 杭州南 / 杭州东-杭州西 / 杭州西 / 杭州-杭州东） |
| `LSZ`（无关站） | ❌ 同上 |
| `XAY`（西安） | ✅ 8 条 |
| `CWQ`（长沙南） | ✅ 10 条 |

**结论**：目的地站码必须过滤；**反方向站码可用**，产出的是绕行方案。是否保留属产品决策（见第五节）。

### 3.3 复核脚本

归档于 [`spike/recheck/`](../spike/recheck/)，均为可直接运行的 Node 脚本（Node 24 原生 fetch，零依赖）：

| 脚本 | 验证内容 |
|---|---|
| `t.mjs` | 城市代表站展开（长沙 / 徐州 / 武汉） |
| `t2.mjs` | 无关枢纽 / 反方向枢纽 / 目的地自身 |
| `t3.mjs` | 站级码 vs 城市级码（成都东 → 自贡） |
| `t4.mjs` | 非同名车站码是否触发城市展开 |
| `t5.mjs` | 小站展开行为（上海西 / 安亭北 / 龙泉寺等） |
| `t6.mjs` | 兰州西在不同 OD 下的展开差异 |

## 四、合规边界

设计方案第 9 节定位：**个人低频查询，不对外提供数据服务、不批量抓取、不抢票**。

公开部署会越过这条线，且代理请求从云厂商**共享 IP** 发出，比家宽更容易触发风控。因此：

- **阶段一（localhost）** 与定位一致，无合规风险；
- **阶段二（Workers 公开访问）** 需重新评估，建议至少加访问口令限制范围。

**不做**：自动下单、验证码识别、多账号、绕过风控。
