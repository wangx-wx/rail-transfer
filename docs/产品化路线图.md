## 零、先说清楚：这是形态变更，不只是加功能

当前定位是**个人低频自用**：

- `D2`：代理层归属「仅自己 + 朋友」，加访问口令，不公开无门槛提供
- `D31` / README 合规声明：不对外提供数据服务、不批量抓取

本路线图的终点是**公开产品**：有用户体系、消耗积分、全网推广。这与 `D2` 直接冲突，
**不是加几个功能就能到达的**。所以整条路线有一个必须先拍板的分岔：

| 选择 | 后果 |
|---|---|
| **A. 走公开产品路线** | 需要主体资质、备案、合规边界重写；`D2`/`D31` 需被新决策取代 |
| **B. 只做小程序、维持自用** | 只做阶段 B；阶段 C（用户/积分）与 D（推广）全部不成立 |

下面按 A 路线写。选 B 的话，直接砍掉 C 和 D。

## 一、前置条件（不做这些，后面全部卡住）

这几项不是「技术实现」，是**能不能开工**的问题，且都有外部审批周期，建议最先启动。

| 项 | 卡点 |
|---|---|
| **小程序主体** | 个人主体可选服务类目有限，出行/交通类查询通常要求企业或个体工商户资质。先对照微信当前类目表确认，再决定用哪个主体注册——主体一旦注册，改名很麻烦 |
| **小程序备案** | 境内小程序须完成备案才能发布，有审核周期 |
| **请求域名** | 小程序只能请求后台配置过的 HTTPS 域名，且该域名需 ICP 备案。当前 Worker 跑在 Cloudflare，`workers.dev` 无法备案 → 需要自有已备案域名 |
| **接口合规** | 12306 未开放 API，本项目依赖其内部接口。自用属灰色地带；**公开产品 + 积分收费会显著抬高风险等级**。这一条可能直接决定路线 A 走不走得通，建议在写任何代码前先想清楚 |
| **虚拟支付** | 小程序内销售虚拟商品受平台规则限制（iOS 尤其严格）。积分若支持购买，需先确认合规路径；若积分只能靠签到/邀请获得，则无此问题 |

## 二、阶段划分

四个阶段，顺序即依赖顺序。阶段内的编号沿用你列的原始条目。

### 阶段 A：定身份（原 3 → 4）

产品得先有名字和一句话，才谈得上注册、海报和推广。

- **A1｜定名称**（原 3）
  - 名称即小程序名称，注册后改名成本高，必须早定
  - 要定的：中文名、是否有英文名、与「rail-transfer」仓库名的关系、名称可用性（是否被占用）
  - 影响面：小程序注册、域名、公众号（若同名）、所有推广素材

- **A2｜定口号**（原 4）
  - 一句话说清「比官方多给你多少方案」，这是本产品唯一的核心价值
  - 要定的：主口号（长期用）、副文案（分场景换）

- **A3｜视觉基调**（原 4 的「海报」）
  - 不是具体海报，是**一套可复用的视觉语言**：主色、字体、版式调性
  - 与现有 Web 的关系：现有版式（`D79` 时刻表风格、颜色只作信号）已经成型，建议直接沿用为品牌基调，而不是另起一套
  - 产出：视觉规范 + 1 张主视觉

> **阶段 A 的产出是阶段 B 和 D 的共同输入。** 海报素材（D 阶段）从这里派生，不重复设计。

---

### 阶段 B：上小程序（原 1 → 2）

- **B1｜小程序接入**（原 1）
  - 要定的关键方向：
    - **技术路线**：跨端框架复用现有 React 代码 vs 小程序原生重写。这是本阶段最大的一个岔路，直接影响工期
    - **功能范围**：首版是否与 Web 完全对齐（含买短乘长、接驳、自研中转）？还是先只上「查票 + 官方中转」？
    - **代理层形态**：现有 Cloudflare Worker 能否继续用（取决于域名备案怎么解），还是要迁到境内服务器
  - 依赖：阶段 A 的名称（注册用）、前置条件里的主体与域名

- **B2｜小程序版式**（原 2）
  - 方向问题：**沿用 D79 版式语言，还是为小程序重做一版？**
  - 小程序的约束与 Web 不同：屏幕更窄、无 hover、没有浏览器地址栏、页面栈导航、下拉刷新是原生手势
  - 建议方向：**沿用同一套信息结构**（一程一行、换乘断点独立成行、颜色只作信号），但重排交互层级——小程序不适合 Web 那种「折叠面板 + 展开详情」的多层结构，更适合「列表 → 详情页」的两级跳转
  - 依赖：B1 的技术路线确定后才能定稿

---

### 阶段 C：用户与积分（原 5 → 6）

这是从「工具」变成「服务」的一步，也是合规风险最高的一步。

- **C1｜用户体系**（原 5）
  - 要定的：
    - **登录方式**：仅微信授权登录，还是也支持手机号？微信登录可拿到 `openid`，但用户体系是否要跨端（Web + 小程序同一账号）？
    - **存什么**：只存 `openid` + 积分余额，还是要存查询历史/收藏？存得越多，隐私与合规负担越重
    - **后端**：现在没有数据库。用户体系意味着必须引入持久化存储

- **C2｜积分消耗**（原 6）
  - 要定的：
    - **扣分粒度**：按次查询扣？按「自研中转」这种重查询扣更多？还是按天配额折算成积分？
    - **积分来源**：签到 / 邀请 / 完成任务 / 购买。**购买涉及虚拟支付合规**（见前置条件）
    - **防滥用**：免费额度 + 积分制的意义就在于控频。扣分点必须和后端的限流真正挂钩，否则只是装饰
    - **未登录怎么办**：是否保留免登录的少量免费查询
  - 依赖：C1

> 阶段 C 有一个隐含前提：**必须先解决接口合规问题**。前面自用阶段的灰色地带，
> 到了「向用户收积分换查询次数」就变成了明确的商业行为，风险性质变了。

---

### 阶段 D：推广（原 7）

- **D1｜渠道规划**（原 7）
  - 你列的渠道：小红书、抖音、微信公众号、博客
  - 要定的：
    - **优先级**：不建议四个一起铺。小红书/抖音是流量型（要持续产出、看爆款），公众号/博客是沉淀型（要长文、看搜索）。先选一个主阵地
    - **内容形态**：短视频 vs 图文 vs 长文，各渠道不同
    - **转化路径**：小程序码 / 链接如何落到具体渠道（小程序不能直接分享到小红书，通常靠二维码或搜一搜）
  - 素材：海报与口号来自阶段 A，这里只做**具体投放素材**

- **D2｜内容选题方向**（原 7）
  - 本产品天然适合的内容母题：「官方没告诉你的中转方案」「同一趟车为什么拆开买更便宜」这类反直觉选题
  - 方向层面只需要确定：内容是以**工具教程**为主，还是以**出行攻略**为主

- **依赖**：阶段 B 上线（没有落地页，推广无意义）

## 三、依赖关系

```
前置条件（主体 / 备案 / 域名 / 合规 / 支付）
        │
        ├──────────────┐
        ▼              │
   阶段 A 定身份        │
   名称 → 口号 → 视觉   │
        │              │
        ▼              │
   阶段 B 上小程序 ◄────┘
   B1 接入 → B2 版式
        │
        ├──────────────┐
        ▼              ▼
   阶段 C 用户/积分   阶段 D 推广
   C1 用户 → C2 积分  D1 渠道 → D2 选题
```

关键依赖只有三条：

1. **A 在 B 之前**：小程序注册要用名称，且改名成本高
2. **B 在 C 之前**：没有小程序，用户体系无处落地
3. **B 在 D 之前**：没有落地页，推广是空转

C 和 D 之间**没有依赖**，可以并行；但两者都在抢同一份精力，实际大概率是二选一先做。

## 四、待定问题（进入执行前必须有答案）

1. **路线 A 还是 B**——公开产品，还是小程序仅供自用？这一条决定后面 70% 的内容是否成立
2. **接口合规的底线在哪**——公开到什么程度、是否收费，直接决定风险性质
3. **主体用哪个**——个人 / 个体户 / 公司，决定可选类目与备案路径
4. **小程序是否重写**——跨端复用还是原生重写，决定阶段 B 的工期量级
5. **积分是否可购买**——决定要不要碰虚拟支付
6. **推广主阵地选哪个**——四个渠道一起铺，在起步阶段大概率都做不好
